Severity key used here: S3 is a major validity, reproducibility, or central-question blocker for empirical completion; S2 is a substantive but bounded scientific or reporting repair; S1 is a local claim-scope or wording repair; S0 is cosmetic. Evidence is reported separately from severity.

The draft is unusually clear about its current evidence boundary. The abstract, Results, Limitations, Conclusion, and story specification state that quality runs and scores are unavailable, and the score table contains placeholders rather than fabricated values. The historical ROUGE values in the implementation plan are not imported into this manuscript and must remain excluded from claims about the proposed graph. The active graph is implemented under `src/eviseq_new`; its default `architecture.name` is `afmr_value_anchor`, while the same package also retains `afmr_v1` as a shared-memory control. The local suite passed 94 tests, and the model-free smoke run completed with `status: ok` using tiny randomly initialized backbones and grounded copy enabled. Those are implementation-contract checks only; they do not establish factuality, ROUGE, BERTScore, superiority, portability, or hardware efficiency.

## Priority-ranked action items

1. **ARCH-01 — S3, confirmed, open; scope: validity/reproducibility.** The paper’s Appendix table (`main.tex`, lines 96--111) says `afmr_base.yaml` is the configuration authority and that task recipes override only model paths, data paths, lengths, and resource settings. The actual PubMed recipe (`src/eviseq_new/configs/afmr_pubmed.yaml`, lines 16--33) overrides the architecture materially: controller 384 instead of 256, depth rank 256 instead of 128, feature rank 512 instead of 256, focus hidden size 384 instead of 256, a fourth 1024-token window, and different gate caps/initializations. The base recipe also names `Qwen/Qwen3-Embedding-0.6B`, whereas the paper’s anchor is `PPLX-Embed v1 0.6B`; the PubMed and ArXiv recipes use placeholder PPLX paths. Equations and the Appendix therefore do not identify one reproducible proposed configuration. The code additionally permits `afmr_v1`, for which the value-anchor equations do not apply. Resolve one configuration authority before any run is called an EviSeq result: either remove the task architecture overrides or describe and lock each profile in the paper. State that `afmr_value_anchor` is the only main method and reserve `afmr_v1` for an explicitly named control. Affected: Method, Experiments, Appendix, RQ1--RQ4 tables, story-spec method facts, and every checkpoint/manifest gate. Authority needed: the locked config decision in the story specification and plan Sections 1, 5, 7, 27, and 28, plus the resolved YAML used for each run.

2. **FAIR-01 — S3, confirmed, open; scope: comparison validity.** Plan Section 1.3 requires the official AFMR/T5Gemma comparison to use an empty textual decoder prompt so that AFMR does not receive an extra instruction unavailable to T5Gemma. The active base and task YAMLs set a long nonempty `decoder_prompt` and `decoder_chat_template: true`; the README explicitly describes this different Qwen decoder conditioning and says it must be reported. The manuscript instead says the systems share task-instruction content and describes the comparisons as matched protocols (`method_experiments.tex`, lines 274--281; `results_discussion.tex`, lines 49--63), without resolving the T5Gemma decoder-input difference. This is a direct confound for RQ1/RQ2 baseline attribution. Choose and freeze the official contract: use an empty decoder prompt/BOS or EOS start as required by the plan, or retain the richer prompt but describe the conditioning difference, treat it as a separate ablation, and remove “matched” language where it is not true. Record the exact source prefix, chat template, prompt, prefix, and generated-token constraints for every baseline. Affected: Abstract, Introduction, Experiments, Results templates, Appendix, and prediction manifests. Authority needed: the final comparison protocol and exact T5Gemma recipe.

3. **RQ3-01 — S3, confirmed, open; scope: question-to-method alignment.** The paper asks which of the encoder, AFMR bridge, and grounded-copy route is necessary and specifies no-encoder, no-bridge, and no-grounded-copy controls. `src/eviseq_new` has a copy on/off configuration and the `afmr_v1`/`afmr_value_anchor` branch, but no no-encoder model, no-bridge implementation, or corresponding configs and tests. The only explicit ablation matrix in the plan (Section 19) instead enumerates A0--A7 depth, feature, focus, prompt, budget, and historical allocation variants; it does not implement the paper’s three controls, and the CE-only cleanup in Section 28 removes allocation supervision from the main graph. Implement the stated controls in `eviseq_new` with fixed decoder, train-from-pretrained initialization, and recorded parameter/compute budgets, or rewrite RQ3 and its Results template to match the controls that actually exist. Keep “necessary” local to the registered graph and benchmark; an ablation cannot support universal causal necessity. Affected: RQ3, the Results table, Discussion, experiment scripts/configs, and the claim--evidence map.

4. **RQ1-01 — S3, evidence: unverified, open; scope: estimand and claim scope.** RQ1 asks whether EviSeq reduces unsupported entities, numbers, and relations. The registered evidence is native AlignScore consistency, with a manual factual-error audit described only as “where available”; AlignScore is a proxy and the manuscript itself correctly says it does not establish a reduction in factual errors. The current `src/eviseq_new` package contains no AlignScore implementation or audit protocol. Thus the current evidence route can answer change in the selected source--summary consistency proxy, but cannot answer the category-level factual-error question as written. Either narrow RQ1 and its answer template to “change in AlignScore consistency under this benchmark,” or make a held-out, category-coded factual audit mandatory and pre-specify sampling, annotation rules, adjudication, and aggregation. Keep `1-AlignScore` as a direction transform, never a probability. Affected: RQ1 in the Introduction, Metrics, Results template, Discussion, Abstract, and Conclusion. Authority needed: the final factuality estimand, AlignScore version/checkpoint/chunking, and any human-audit protocol.

5. **EVAL-01 — S3, confirmed, open; scope: reproducibility/evidence production.** The paper says the implementation and metric protocol are available, but the package’s `evaluation/metrics.py` implements only diagnostic Python `rouge==1.0.0`. There is no Perl ROUGE-1.5.5 adapter, AlignScore runner, BERTScore runner, paired-bootstrap analysis, source-copy-rate computation, or complete truncation/latency/peak-memory report in the package. `run_pubmed_pair.sh` can call an external ROUGE wrapper only when `ROUGE155_SCRIPT` is supplied. The code/config tree contains PubMed, ArXiv, CNNDM, and WikiLingua recipes, but no BookSum or GovReport recipe or manifest. The manuscript properly calls those two datasets pending, so this is an open readiness limitation rather than an invented result. Change “metric protocol are available” to “the evaluation specification is described” until the scorers and manifests are supplied; add immutable model/tokenizer identifiers, exact scorer settings, four dataset manifests, prediction files, and paired intervals before filling any score cell. Affected: Abstract, Reproducibility, Metrics, all Results tables, and release artifacts. Authority needed: scorer wrappers/checkpoints, dataset field/split manifests, and the final prediction provenance contract.

6. **EQ-01 — S2, confirmed, open; scope: notation and implementation fidelity.** The controller equation in `method_experiments.tex`, equation (\ref{eq:controller}), writes `RMSNorm(W_h\bar h + W_p\bar p + MLP(...))`. The implementation first applies separate RMSNorm modules to the pooled source and prompt (`src/eviseq_new/eviseq_afmr/modeling/controller.py`, lines 17--24 and 36--41), then projects them, adds the budget branch, and applies the output RMSNorm. Plan Section 7.1 agrees with the implementation. Replace the paper equation with `RMSNorm(W_h RMSNorm(\bar h) + W_p RMSNorm(\bar p) + MLP(...))` or define the symbols so the two input normalizations are explicit. Document the nonnegative budget clamp if it is part of the locked implementation. Affected: Method equation, notation ledger, and implementation contract.

7. **COPY-01 — S2, confirmed, open; scope: architecture equation/provenance.** The copy equation defines `A^{copy}_{t,j}` but omits that the code adds an alignment-weighted source-prior bias to the copy logits. `GroundedCopyHead.prepare` pools `source_bias` into `CopyState.bias` and `distribution` adds it before the copy softmax (`grounded_copy.py`, lines 71--92). Define `j` as an eligible decoder-token/source-span row, state the overlap pooling, and include `+\tilde b_j` in the copy attention logits. Keep the repeated-token-ID marginalization and no-eligible-source fallback explicit. Without this term, a reader implementing the displayed equations will produce a different graph. Affected: Method copy subsection, plan tensor contract, and reproducibility description.

8. **MEM-01 — S2, confirmed, open; scope: resource and tensor-contract clarity.** The text says the bridge has “one full source memory” and “no second source bank,” while the value-anchor path materializes both `BridgeState.memory` and `BridgeState.value_memory`, each aligned over the source sequence. The copy head also creates a sparse copy-key state. This does not contradict the intended absence of a separate hard-selected full bank, but the current wording and the plan’s “only one tensor memory” invariant can be read as a false one-tensor claim. State precisely that the graph retains one full retrieval memory plus one aligned value tensor for key/value separation, with no pruned source bank; disclose the resulting memory/latency cost. Affected: Problem setting, decoder method, README/plan tensor contract, and efficiency diagnostics.

9. **RQ4-01 — S2, confirmed, open; scope: coverage and transfer inference.** RQ4 promises PPLXEmbed, QwenCausal, QwenEmbed, and NemotronEmbed on all four datasets. The generic encoder adapter can load a compatible local `AutoModel`, but the package has no variant configs, immutable identifiers, or transfer-run manifests for QwenCausal or NemotronEmbed, and no BookSum/GovReport preparation. The Discussion appropriately notes directionality, tokenization, width, pretraining, and capacity confounding; those limits should be attached to the RQ itself. Add executable configs and adapter checks for every variant or narrow RQ4 to the variants actually supported. A result from one encoder choice can support portability only to that tested choice. Affected: RQ4, experiment matrix, Results template, and portability claim.

10. **NOVEL-01 — S2, evidence: unverified, open; scope: contribution boundary.** The paper correctly says it does not claim novelty for generic checkpoint reuse, cross-attention, copying, or multi-scale source reasoning. Its remaining contribution is an integration at the interface: depth-selective and feature-wise residuals, a soft source prior, key/value separation, and grounded copy. The related-work section does not yet establish the closest composed encoder--decoder interface or explicitly distinguish the implementation from the depth-selective, constrained-residual, coarse-to-fine, and feature-wise precedents named in the plan. Present AFMR as an interface integration hypothesis and adaptation of those principles, avoid claiming a new primitive, and add a systematic closest-work comparison before using any “novel” or “to our knowledge” wording. Only ablations can support an effectiveness contribution; implementation and unit tests support execution properties. Affected: Introduction contributions, Related Work, and Discussion. Authority needed: primary papers and a completed closest-work search.

11. **COPY-02 — S1, confirmed, open; scope: claim wording.** The abstract says the grounded copy head “preserves source lexical forms and numbers.” The code provides a learned copy route whose gate can still select the LM distribution, and the paper later acknowledges that copying is not factual verification. Replace “preserves” with “provides a route for copying” or equivalent capability language. Do not promote this capability to an outcome until held-out predictions and an explicit copy diagnostic support it.

## Question and evidence coverage

| Question | Coverage in the manuscript | Current evidence route | Scientific status |
|---|---|---|---|
| RQ1 factuality | All four datasets are named and the direction of AlignScore is defined | AlignScore is not implemented here; category-level error reduction needs an audit | Proxy question is feasible; the direct wording remains unsupported |

The architecture equations otherwise track the default value-anchor graph: four normalized taps, token-wise depth softmax, zero-initialized low-rank depth and feature residual outputs, bounded focus strength and temperature, full visible source positions, a shared source prior, copied cross-attention in every decoder layer, final-state value projection, offset-based copy alignment, repeated-ID marginalization, CE-only training, and source/prompt/budget inputs available at inference. The two equation-level repairs above and the task-configuration conflict must be resolved before the equations can be treated as the authority.

The main claim boundary is currently safe in Results, Discussion, Limitations, and Conclusion: implementation checks are separated from quality outcomes, and no ROUGE, AlignScore, BERTScore, factuality, ablation, or portability result is asserted. The remaining unsupported or overbroad formulations are the abstract’s “metric protocol are available,” “preserves” wording, RQ1’s category-level estimand, and “matched” comparison language under the active prompt configs. The plan’s historical ROUGE table and any README statement about earlier audited predictions are not evidence for this manuscript and must not be promoted into it.

Before the next stage, resolve the configuration and prompt authority, add or explicitly scope the missing RQ3/RQ4 controls and metric/data artifacts, correct the controller and copy equations, state the two-tensor key/value memory contract, and then run the registered four-dataset predictions from `last.pt` under greedy decoding. Only after manifests, scorer outputs, paired intervals, diagnostics, and any factuality audit are present should the fill-in templates become declarative answers.
